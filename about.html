Simple File Encryptor 3.0

Private file encryption, kept simple.

Everything here is designed to explain what SFE is doing in plain language first. Your files stay on your device while the app protects or restores them.

Version 3.0 features:

🔐

Argon2id + PBKDF2

SFE3 supports modern Argon2id as the recommended KDF and PBKDF2-HMAC-SHA-256 as an alternate, widely supported option.

🛡️

AES-256-GCM

Authenticated encryption protects the SFE3 header, encrypted manifest, and every encrypted data record.

📦

Chunked SFE3

New SFE3 encryption processes data in fixed 1 MiB records so large files do not require one giant plaintext buffer.

📁

Private container metadata

New encrypted containers keep names, paths, file counts, exact file sizes, and other manifest metadata inside authenticated ciphertext.

⚡

Fully local

File data and passwords stay inside your browser while encryption or decryption is running.

🌐

Offline-ready

The release contains its runtime code locally, so no CDN, account, or internet connection is required after loading.

How encryption works

  1. Select your files. The browser reads selected data locally. Nothing is uploaded.
  2. Build an encrypted manifest. Names, relative paths, and exact sizes are placed inside a fixed-size encrypted manifest instead of being stored in a plaintext ZIP.
  3. Derive a key. SFE3 derives an AES-256 key using Argon2id or PBKDF2-HMAC-SHA-256 with a fresh 32-byte salt.
  4. Encrypt in fixed-size records. File data is processed in 1 MiB chunks with zero padding in the final chunk so individual file boundaries and exact sizes are not exposed by the container records.
  5. Authenticate every record. AES-256-GCM authenticates the public SFE3 header, record type, and record index, preventing parameter, ordering, or ciphertext tampering.
  6. Use an opaque filename. New encrypted downloads use a cryptographically random filename such as a 32-hex-character identifier followed by .sfe3.
  7. Download the result. The encrypted container remains local and is never uploaded by the application.

Argon2id is the recommended SFE3 KDF. PBKDF2-HMAC-SHA-256 is included when a widely supported, standards-oriented KDF is preferred. Passwords are normalized with Unicode NFC for new SFE3 derivation.

Salt, nonce and KDF costs

Salt

SFE3 uses a fresh 32-byte random salt for every container. The salt is public metadata and is required for password-based key derivation; it is not intended to be secret.

Nonce

SFE3 creates a fresh random 12-byte nonce base for every container. A record counter is added to that base to produce a unique 96-bit AES-GCM nonce for every manifest and data record under the derived AES key. The nonce is authenticated but does not need to be secret.

Argon2id

The default Argon2id profile is 64 MiB, 3 passes, and 4 lanes. SFE3 exposes custom memory from 12–256 MiB. The implementation is local and based on RFC 9106. Higher memory settings increase the resources required for password guessing but also increase device RAM use.

PBKDF2

SFE3 uses PBKDF2-HMAC-SHA-256 with 600,000–2,000,000 iterations; 600,000 by default. PBKDF2 is an alternative KDF; Argon2id remains the preferred choice for new files.

The SFE3 file format

The public SFE3 header contains only what is required to select the decryption algorithm and reproduce key derivation: version, KDF identifier, cipher identifier, KDF parameters, a 32-byte salt, and a 12-byte nonce base.

SFE3 header | encrypted fixed-size manifest record | encrypted fixed-size data records

The header is authenticated as AES-GCM additional authenticated data. Every record also authenticates its type and record index. New containers therefore do not need a plaintext ZIP or per-file plaintext names.

Metadata protection

  • Original filenames are not used as the encrypted download filename.
  • Folder paths are stored only inside the encrypted manifest.
  • File count and exact per-file sizes are stored only inside the encrypted manifest.
  • File MIME types and filesystem timestamps are intentionally not stored by SFE3.
  • Each data record is fixed-size; the final record is padded so the exact plaintext length is not directly encoded in the record size.
  • The overall container size still reveals an approximate amount of encrypted data. SFE3 reduces metadata leakage but cannot make file size information disappear without potentially very large padding.

Privacy & limitations

  • Your files are processed locally in the browser.
  • Your password is not stored or transmitted by the application.
  • There are no accounts, cloud uploads, advertisements, analytics, or tracking built into the application.
  • Individual files up to 1 GB are accepted. New SFE3 processing is chunked, but browser and device limits still apply.
  • A forgotten password cannot be recovered. Keep a secure backup of important encrypted files and their passwords.
  • This project has not undergone an independent cryptographic security audit; the browser, operating system, and release files remain part of the security boundary.
